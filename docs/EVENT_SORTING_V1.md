# 행사 정렬 규칙 v1

## 확인 범위

운영 D1/API를 호출하지 않고 `.wrangler/deployment/tourapi-real.json` snapshot과 현재 Worker/frontend 코드를 확인했다. snapshot 행사 263건을 날짜 범위와 로컬 comparator에 적용했다.

현재 서버의 날짜 정렬은 SQL `ORDER BY e.start_date,e.id`이며, pagination 전에 적용된다. 거리순을 선택하면 서버가 반환한 행사에 대해 `distance_km → start_date → id`로 정렬한다. 기본 UI label은 `날짜순`이고 기본값도 날짜순이다.

## 후보 비교

날짜 기준은 2026-09-19을 오늘로 사용했다.

| 모드 | 겹치는 행사 | 기존 A: 시작일 ASC | 후보 B: 기간 내 신규 시작 우선 | 후보 C: relevant date |
| --- | ---: | --- | --- | --- |
| 오늘(9/19) | 119 | 2022·2026-01 시작 장기 행사가 상위 20건 전부 | 9/19 신규 시작 행사 20건이 상위 20건 | B와 동일 |
| 이번 주말(9/19~20) | 120 | 장기 행사 20건이 상위 20건 | 9/19~20 신규 시작 행사 20건 | B와 동일 |
| 다음 주말(9/26~27) | 68 | 장기 행사 20건 | 9/26 신규 시작 1건 후 기존 진행 행사 | B와 동일 |

기존 A는 실제 선택 기간에 새로 시작하는 행사를 장기 행사 뒤로 밀어 발견성을 떨어뜨린다. 후보 C의 `max(start_date, selected_start)` relevant date는 이미 진행 중인 행사 모두가 선택 시작일을 공유하므로 후보 B와 같은 결과가 된다. 기간 길이를 점수화하거나 장기 행사를 숨기지 않는다.

## 최종 날짜순 v1 계약

선택 기간과 겹치는 행사에 대해 다음 순서로 정렬한다.

1. 선택 기간 안에 시작하는 행사 우선
2. `start_date` 오름차순
3. `end_date` 오름차순
4. `id` 오름차순

`shared/event-sorting.ts`의 `compareDateOrder`가 이 계약을 순수 함수로 표현한다. 날짜 필터가 오늘·이번 주말·다음 주말·특정 날짜·기간 어느 것이든 API가 계산한 선택 범위를 넘겨 동일하게 적용한다. 원본 시작·종료일이나 사용자 표시 날짜는 바꾸지 않는다.

이번 단계에서는 서버 pagination 정렬을 변경하지 않았다. 실제 운영 적용 시 SQL `ORDER BY`에 선택 범위의 신규 시작 여부를 deterministic CASE로 포함해야 하며, frontend가 첫 페이지 결과만 재정렬해서 전체 정렬처럼 보이게 해서는 안 된다.

## pagination 안정성

현재 SQL은 `start_date, id`를 사용해 동일 query에서 안정적이다. 후보 v1을 운영 연결할 때도 `start_date, end_date, id`까지 포함하고 신규 시작 CASE를 먼저 두어야 한다. 로컬 snapshot을 page size 9로 순회하는 계약 검토에서 후보 comparator는 duplicate 0, missing 0이 되도록 전체 배열을 한 번만 순회한다. 운영 backend 연결 전까지 기존 server pagination 동작은 유지한다.

## 날짜 모드와 필터

정렬의 기준은 항상 사용자가 고른 범위다. 날짜·지역·콘텐츠·비용·검색 조건이 먼저 행사 집합을 좁히고, 날짜순은 그 결과의 순서만 정한다. reset은 기존처럼 날짜와 필터를 주말 기본값으로 되돌리고 날짜순을 복원한다.

## 장기·하루·종료 임박 행사

장기 행사는 유효한 행사이므로 제거하거나 임의 penalty를 주지 않는다. 단지 선택 기간 내 신규 시작 행사가 먼저 보이도록 한다. 하루 행사나 짧은 행사를 기간 길이만으로 우선하지 않는다. 선택 기간에 실제로 겹치는 종료 임박 행사는 기존 행사 집합에 남으며, 별도 “이번 주말 종료” badge는 이번 단계에서 추가하지 않았다.

## 거리순 향후 계약

좌표가 있는 행사 snapshot은 263/263(100%)이고 invalid 좌표는 0건이지만, 거리순은 사용자 위치가 확보된 경우에만 의미가 있다. 현재 UI는 위치가 없으면 거리순 option을 노출하지 않고, 사용자는 `내 주변 찾기`를 명시적으로 눌러 위치를 확보해야 한다. 위치를 확보하면 거리순을 선택할 수 있고, 위치 해제 시 날짜순으로 돌아간다.

향후 거리순은 `distance → 선택 범위 신규 시작 여부/날짜 key → id` 순서의 deterministic tie-break를 사용한다. 지역과 위치를 함께 쓰는 현재 계약(지역 범위 안 거리순)은 지역 탐색 v1 문서를 따른다.

## 구현·보류

이번 단계에서 사용자에게 새 추천/인기/신뢰/companion 정렬은 추가하지 않았다. 기존 `날짜순` label과 기본 정렬을 유지하고, 거리순은 위치가 있을 때만 선택지로 보이도록 했다. 실제 신규 시작 우선 정렬은 pagination을 책임지는 backend 변경이 필요하므로 helper·테스트·계약만 준비했다. 운영 D1, Worker SQL, schema, Cloudflare는 변경하지 않았다.
